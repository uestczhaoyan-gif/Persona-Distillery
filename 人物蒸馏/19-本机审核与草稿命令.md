# 本机审核与草稿命令

这些命令只供资料所有者在自己的本机终端运行。私人结果不得复制给云 Agent、聊天窗口或公共仓库；不要为了协助调试录制真实私人输出。项目工程测试只使用原创合成夹具。

`local_review.py` 复用已有策略、当前性核验、人工决定、稳定合并和草稿接口，不新增模型调用。所有命令要求 stdin/stdout/stderr 都是终端，并显式确认本地存储；不能重定向输出。inspect 命令会显示私人候选和依据，其余命令仅显示状态、计数和哈希。JSON 保留中文并转义终端控制字节，不执行资料里的指令。

通用前缀（路径和哈希必须替换为本机真实值；不要把私人值发到云端）：

```powershell
python 人物蒸馏/scripts/local_review.py --library D:/LocalPersonaJobs --job sample-job --confirm-local-storage <子命令>
```

| 子命令 | 参数 | 作用 |
| --- | --- | --- |
| inspect-candidate | --run HASH | 核验并显示当前证据/情境候选及片段依据 |
| template-candidate | --run HASH | 显示绑定当前候选哈希和全部编号的空白决定模板 |
| review-candidate | --run HASH --decision PATH | 保存逐项采纳/拒绝/修改决定 |
| merge | 多次 --review HASH；可选 --previous HASH、--decision PATH | 按明确顺序合并审核历史；冲突决定文件只有 resolutions 数组 |
| inspect-spec | --spec HASH | 核验并显示当前人物规范候选与依据目录 |
| template-spec | --spec HASH | 显示绑定当前规范哈希的空白决定模板 |
| review-spec | --spec HASH --decision PATH | 保存规范采纳/拒绝/修改决定 |
| build-draft | --review HASH | 从已采纳规范构建外部 draft/private 包 |
| plan-resume | --review HASH | 预检该草稿构建的中断现场，返回计划哈希 |
| resume-draft | --review HASH --plan HASH | 按刚核对的计划补齐中断构建 |

决定文件是本机 UTF-8 JSON，最多 2 MiB，放在外部非同步、非 Git 目录，且位于任务库、原材料目录及输出人物库之外。调用前先验证任务策略和存储确认。命令不会猜测或自动填写采纳决定，不改写输入决定文件。

候选决定格式见[候选证据与情境契约](14-候选证据与情境契约.md)，冲突格式见[审核历史与增量合并](15-审核历史与增量合并.md)，规范决定格式见[人物规范候选](16-人物规范候选.md)。审核顺序：候选生成 → inspect-candidate → 本机编辑决定 → review-candidate → merge → local_spec.py 生成规范 → inspect-spec → 本机编辑决定 → review-spec → build-draft。

这个终端流程尚无图形编辑器，不自动保存决定模板、不自动选用新模型或重试推理。头像、真实试聊与独立质量审核仍待完成，草稿构建成功不会开放所有功能或授予发布许可。


## M3.7b 空白决定模板

在同一个本机终端用 template-candidate/template-spec 取得模板，复制到自己的外部本地 JSON 编辑器。模板只预填当前哈希与编号，action、reviewer、note、逐项 reason 留空；未经填写无法提交。action 由用户明确填写 accept/reject/edit，edit 另加契约要求的 replacement，不预设批量通过。模板生成再次核验当前来源，不发起模型推理，也不标记审核完成。


## M3.7c 从材料到草稿的执行清单

1. 按[本地任务说明](13-本地蒸馏任务v2.md)初始化外部库，完成人物身份和材料审核，执行 build；遇到 sensitivity_review 先由所有者在本机处理对应审核。确认状态为 review_required，隔离文件按具体原因处理。
2. 在本机确认可用 Ollama 模型及其具体名称，执行 `local_candidates.py --library <库> --job <任务> --model <模型名> --confirm-local-storage --confirm-local-service`。记录返回的 run_sha256。此步骤会实际推理一次，失败不自动重复。
3. 用 inspect-candidate 阅读当前候选与依据，再用 template-candidate 取得空白决定。所有条目分别填写 accept/reject/edit 及理由；在外部本地编辑器保存决定 JSON，然后 review-candidate 保存。记录 review_sha256。
4. 用 merge 的一个或多个有序 --review 参数合并历史。增量时提供 --previous，冲突仍需明确解决；记录 merge_sha256。不要把不同任务的哈希混用。
5. 执行 `local_spec.py --library <库> --job <任务> --merge <合并哈希> --model <模型名> --confirm-local-storage --confirm-local-service`。这会单独进行一次规范候选推理，记录 spec_sha256。
6. inspect-spec 核对规范及依据，template-spec 生成空白决定，填写后 review-spec 保存，记录新的 review_sha256；不要误用第 3 步的证据审核哈希。
7. build-draft 使用第 6 步的规范审核哈希。草稿在配置中的输出人物库 `<build_sha256>/<person-id>/`。若构建中断，先 plan-resume，再用返回的计划哈希 resume-draft；不要手工删标记或覆盖文件。
8. 草稿仍需实际 AI 头像、真实试聊及独立质量检查。资料所有者可按[私人本地预览](../直接对话/docs/私人本地预览.md)显式预览；来源被撤回或改动后，旧草稿会拒绝加载，须按新材料重建。

工程证据：原创虚构材料、两次模型桩响应、模板填写、两个审核阶段、合并、草稿及本地上下文读取已在一条集成测试中串联；来源撤回后拒绝加载。该测试不是实际 Ollama 运行、真实人工盲评或完整人物验收。
